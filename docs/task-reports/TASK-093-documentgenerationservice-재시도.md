## 재시도 동작
두 가지 문제를 서로 다른 횟수로 다룬다.

| 문제 | 어떻게 | 근거 |
|---|---|---|
| AI 서비스가 바쁘거나 응답 없음 (`retryable` 오류) | 최대 3번 다시 시도. 대기 `2×2ⁿ초 + 0~1초 지터`(2, 4, 8초 + 지터), 최대 60초. 마지막 실패 뒤에는 기다리지 않고 오류를 던진다 | FR-090, FR-097 |
| 응답이 올바른 문서가 아님 | 문제를 알려 주는 "수정 요청"을 덧붙여 최대 2번 다시 요청. 대기 없음. 온도를 0 → 0.4 → 0.7로 올린다 | FR-096 |
| 요청 거절, 차단된 프롬프트, 키 없음, 프로그램 버그 | 재시도 없이 즉시 전달 | |

- 두 횟수는 따로 센다(예: 바쁨 → 잘못된 응답 → 바쁨 → 성공이 가능). 바쁨 재시도의 대기는 매번 가장 짧은 값부터 다시 시작한다.
- 품질 재시도가 모두 실패하면 `DocumentGenerationError`(코드 `document_generation_failed`, `problems`, `model_calls`)를 던진다. 서비스 재시도가 모두 실패하면 마지막 `AIServiceUnavailableError`가 그대로 올라간다.
- `on_retry` 콜백으로 재시도 직전 알림(`RetryEvent`)을 받을 수 있다. 호출하는 쪽이 "재시도 중..." 안내(FR-093)를 보여 주는 데 쓴다.

## 응답 검증과 정리
응답은 `OUTPUT_SKELETON`(T092)과 같은 구조여야 한다. 모든 문제를 모아서 알려 주고, 문제가 없으면 정리된 내용을 돌려준다.
- 정리해서 통과시키는 것: 스키마에 없는 필드 삭제(어느 깊이든), 챕터 제목은 항상 고정값, 개념·실수가 5개를 넘으면 5개로 자름(FR-029, FR-034), 단계 번호를 1부터 순서대로, 파일이 하나뿐이면 4장의 파일 경로를 그 파일로 보정, 마크다운 코드 펜스로 감싼 JSON 허용.
- 문제로 보는 것: 챕터 빠짐, 필드 빠짐, 타입이 다름, 비어 있는 핵심 필드, 빈 목록, 실수가 3개 미만, 스켈레톤의 예시 문구(`<개념 이름>` 등)나 `[TODO]`가 그대로 남음, 4장 항목의 파일이 업로드한 파일이 아님, 4장 줄 번호가 파일 범위(1 ≤ 시작 ≤ 끝 ≤ 줄 수) 밖임, JSON이 아님.
- 4장의 `analogy`, `alternatives`, `notes`, `syntax_breakdown`과 5장의 `data`는 비어 있어도 된다(사소한 줄에서 모델이 비우는 것이 자연스럽고, 거부하면 비싼 재시도만 늘어난다).
- **문제 문구에는 모델이 쓴 문장을 절대 싣지 않는다.** 수정 요청에 들어가는 문구는 필드 경로(`chapter4.explanations[0].file: …`)로만 만든다. 모델의 출력이 다음 프롬프트로 되돌아가 주입 경로가 되는 것을 막기 위해서다(테스트로 고정). 수정 요청에는 문제를 최대 10개까지만 싣고 나머지는 개수만 알린다.

## 실제 Gemini로 확인한 것 (임시 스크립트, 호출 4회)
- 단일 파일, 속임수 주석이 든 코드, 두 파일 업로드(`models.py`, `main.py`) 모두 **첫 호출에서 검증 통과**(`model_calls=1`, 재시도 알림 0건). 각 17~18초, 입력 약 1,900토큰, 출력 약 2,200~2,700토큰, 생각 토큰 1,000~1,400.
- 두 파일 업로드에서 4장 항목의 파일 경로가 `main.py`, `models.py` 두 파일 모두에 걸쳐 올바르게 나왔고, 3장 `file_breakdown`의 키도 두 파일이었다.
- 잘못된 키로 호출하면 `AIRequestRejectedError`(400)가 대기 0회, 호출 1회로 바로 올라온다(0.7초).
- **재시도 경로는 실제 서버로는 확인하지 못했다.** 실제 서버를 일부러 "바쁨" 상태로 만들 수 없고, 응답 검증 실패도 실제로는 일어나지 않았다. 이 경로들은 가짜 클라이언트를 쓴 단위 테스트가 지킨다.

## 기술 결정
- **서비스는 파일 내용을 받는다**(`PromptFile` 목록). DB와 저장소 접근은 호출하는 쪽(T094)이 한다. 그래야 서비스를 DB와 네트워크 없이 테스트할 수 있다.
- 시간과 난수를 주입할 수 있게 했다(`sleep`, `jitter`). 테스트가 실제로 기다리지 않고 대기 시간을 정확히 검증한다. 기본값은 `asyncio.sleep`과 `random.random`이다.
- `max_output_tokens`는 지정하지 않는다. T091에서 확인한 대로 생각 토큰이 한도에 포함되어, 한도를 두면 텍스트 없이 끝날 위험이 있다. 요청 하나의 시간 제한은 150초(`request_timeout`)다.
- 첫 요청의 온도는 0이다(같은 코드는 같은 구조, FR-039). 같은 온도로 다시 물으면 같은 오답이 나오기 쉬워 수정 요청마다 올린다.
- 토큰 사용량은 받은 모든 응답의 합계로 돌려준다(비용 계산용). 알 수 없는 값은 0으로 센다.

## 비고
- **구현하지 않은 것**: FR-096이 그다음 단계로 든 (a) 일부 챕터가 실패해도 5개 이상이면 받아들이는 부분 수락, (b) AI 없이 코드 구조에서 기본 문서를 만드는 템플릿 생성. 이 서비스는 "검증을 통과한 문서 하나, 아니면 분명한 오류"만 돌려준다. 이 둘은 문서 형식(실패한 챕터를 어떻게 표시할지)과 화면까지 걸리는 별도 결정이라 후속 작업으로 남긴다.
- **오류 응답 매핑**: `document_generation_failed`와 AI 오류 코드들은 아직 API 오류 표(`DOMAIN_ERROR_STATUS`)에 없다. 문서를 요청하는 엔드포인트(T097~T098)를 만들 때 정해야 한다.
- **화면 표시**: HTML 태그는 검사하지 않는다. HTML을 올린 학습자의 설명에는 태그가 정상적으로 들어가기 때문이다. 문서는 어디서든 텍스트로만 표시해야 한다(HTML로 렌더링 금지).
- 문서가 길 때는 응답이 커진다. 500줄에서의 소요 시간과 한도(FR-025의 3분)는 13줄 기준의 이번 측정(약 18초)으로는 알 수 없고, 큰 코드로 따로 확인해야 한다.
- 요구사항 부록의 "챕터당 100~5,000자" 검사는 넣지 않았다. 4장(줄별 설명)이 길어질 수 있어 맞지 않는다.
